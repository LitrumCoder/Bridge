# Bridge — архитектура

Статус: черновик этапа 1, ждёт подтверждения. Ключевые решения с альтернативами — в [docs/adr](adr/).

Bridge объединяет устройства одной сети в одно рабочее место: общий курсор и клавиатура, перетаскивание
файлов курсором между устройствами, общий буфер обмена, проброс MIDI. Платформы: Windows 10/11,
macOS 13+, Linux (X11, Wayland), Android 10+.

## 1. Принципы

1. **Sans-IO ядро.** Вся логика (сессии, маршрутизация ввода, геометрия, часы, jitter-буфер, состояния)
   написана как детерминированные конечные автоматы: на вход события и время, на выход действия.
   Никаких сокетов, потоков и вызовов ОС внутри `core` и `protocol`. Это даёт тестируемость без ОС,
   property-тесты на инварианты и возможность гонять логику прямо в потоке low-level hook'а, где нельзя
   ждать async (решение о «проглатывании» события принимается синхронно за микросекунды).
2. **Ядро не знает о функциях.** Ввод, буфер, файлы, MIDI — модули за трейтом `Feature`. Новая функция =
   новый crate + одна строка регистрации в демоне.
3. **Ядро не знает о транспорте.** QUIC — одна реализация трейта `Transport`. BLE, Wi-Fi Direct, кабель и
   relay добавляются реализациями того же трейта.
4. **Пир всегда недоверенный.** Любые байты от сети проходят через ограниченный декодер и валидацию.
   Спаренный пир тоже может быть скомпрометирован.
5. **Нет режима без шифрования** и нет «временных» обходов аутентификации.
6. **Ничего не залипает.** Каждое нажатие, доставленное на устройство, получает отпускание на том же
   устройстве — либо от пользователя, либо синтетическое при любом сбое. То же для MIDI-нот.

`protocol` и `core` не зависят от `tokio`, `quinn`, `platform`, `windows`, `objc2`, `x11rb`.

### 2.2. Процессы

- **Демон `bridged`** — один на пользовательскую сессию ОС. Не системная служба: перехват и инъекция ввода,
  буфер и drag&drop живут в пользовательском рабочем столе. Автозапуск: Windows — ключ `Run` в HKCU,
  macOS — LaunchAgent, Linux — systemd `--user` unit (и XDG autostart как запасной вариант).
- **Desktop-приложение** — трей-резидент, автозапускается вместе с демоном. Закрытие окна сворачивает в трей,
  «Выйти из UI» закрывает только UI; демон продолжает работать. Если демон не запущен, UI его запускает.
- **CLI** — короткоживущий клиент IPC.
- **Android** — отдельного демона нет: `bridge_node` работает внутри процесса приложения в Foreground Service.

### 2.3. Локальный IPC

- Транспорт: Windows — именованный канал `\\.\pipe\bridge-<SID пользователя>` с DACL только для текущего
  пользователя; Unix — сокет `$XDG_RUNTIME_DIR/bridge/ipc.sock` (macOS — в `~/Library/Application Support/Bridge/`),
  каталог `0700`, проверка UID пира (`SO_PEERCRED`/`getpeereid`).
- Протокол: кадры `u32 длина + postcard`, запрос/ответ с `request_id` плюс подписка на поток событий
  (смена состояния, устройства, прогресс передач, метрики сети и MIDI). Свой номер версии IPC; UI и CLI
  при несовпадении показывают «обновите приложение».
- Почему не JSON: UI-клиент — Rust-часть Tauri, CLI — Rust; JSON нужен только для `bridge status --json`,
  он формируется в CLI.

## 3. Протокол

Подробности — [ADR-0003](adr/0003-wire-format-and-versioning.md).

### 3.1. Соединение и каналы

Между каждой парой устройств — **два QUIC-соединения** через один UDP-сокет:

| Класс канала | Соединение | Механизм | Приоритет quinn | Кто использует |
|---|---|---|---|---|
| `Control` | interactive | bi-stream, открывает инициатор первым | 100 | ядро: Hello, состояния, раскладка, права, часы, сигналы фич |
| `InputMotion` | interactive | QUIC datagrams, побеждает последнее значение | — (datagrams обгоняют потоки) | input |
| `InputEvents` | interactive | долгоживущий uni-stream, упорядоченный | 90 | input: клавиши, кнопки, колесо, вход/выход курсора |
| `Midi` | interactive | долгоживущий uni-stream, упорядоченный | 80 | midi |
| `Clipboard` | interactive | uni-stream на одну выдачу данных | 50 | clipboard |
| `Bulk` | **bulk** | uni-stream на файл | 0 | files |

Почему отдельное bulk-соединение: приоритеты потоков quinn решают, какие данные попадут в следующий пакет,
но не убирают очередь в Wi-Fi-роутере. Передача 2 ГБ, занявшая всё окно перегрузки, добавит
десятки миллисекунд задержки вводу даже при максимальном приоритете. У bulk-соединения свой
контроллер перегрузки с ограничением по задержке (LEDBAT-подобный, цель — не более +2–5 мс к RTT
interactive-соединения), и он уступает полосу всему остальному. Решение — [ADR-0002](adr/0002-transport-quic.md).
Требование «файлы не увеличивают задержку ввода и MIDI» проверяется интеграционным тестом через
симулятор сети с узким горлом и буфером.

`ChannelScheduler` в `core` сопоставляет класс канала с соединением, приоритетом и (в будущем) транспортом.
Фичи никогда не открывают потоки напрямую — только просят канал своего класса.

### 3.2. Кадрирование

- Потоки: `varint длина` + `Envelope`. Длина проверяется против лимита класса канала **до** выделения памяти
  (Control 64 КиБ, InputEvents 4 КиБ, Midi 72 КиБ — SysEx до 64 КиБ, Clipboard 1 МиБ на кадр, Bulk — заголовок
  4 КиБ, затем сырые байты файла без кадрирования).
- `Envelope { feature: FeatureId(u16), kind: u16, payload: [u8] }`. Ядро маршрутизирует по `feature`,
  не разбирая `payload`. Неизвестная фича или неизвестный `kind` — сообщение пропускается и считается
  в метриках, соединение не рвётся (кроме `Control`/0, где это нарушение протокола).
- Datagrams: `[версия формата u8][FeatureId varint][payload]`, максимум — `max_datagram_size` соединения.
- Кодек — postcard (компактный, детерминированный, задокументированный стабильный формат). Декодер работает
  с ограничением глубины и длины коллекций; типы протокола не рекурсивны.

### 3.3. Версионирование

- `PROTOCOL_VERSION = (major, minor)`. Major — несовместимые изменения конверта/рукопожатия; minor — новые
  сообщения и фичи.
- **Правило эволюции:** опубликованную структуру сообщения не меняют. Новое поле = новый `kind` или новая
  версия фичи. Это компенсирует то, что postcard не самоописывающий.
- Каждая фича объявляет диапазон поддерживаемых версий; при рукопожатии выбирается максимальная общая,
  фичи без пересечения отключаются для этого пира (UI показывает «на устройстве X старая версия: MIDI недоступен»).
- Major не совпал → `Reject { IncompatibleVersion { ours, theirs } }` и закрытие с кодом `INCOMPATIBLE_VERSION`.

### 3.4. Рукопожатие

```
Инициатор (A)                                         Ответчик (B)
 QUIC + TLS 1.3, ALPN "bridge", сертификаты обеих сторон
   ── проверка: отпечаток B закреплён (или режим сопряжения) ──
                                         ── проверка: отпечаток A в доверенных (или окно сопряжения открыто) ──
 Control: ClientHello{proto, app, device_id, name, platform, features[], intent: Normal|Pair, resume?} ──►
                                    ◄── ServerHello{proto, ..., features[], negotiated[]}  |  Reject{reason}
 ◄──────── обмен: DeviceState, Permissions (что я разрешаю тебе), LayoutDigest, ClockSync ─────────►
 ── сессия Active: открываются InputEvents/Midi потоки, datagrams ──
```

Коды закрытия QUIC (application error): `0 NORMAL`, `1 NOT_PAIRED`, `2 INCOMPATIBLE_VERSION`, `3 REVOKED`,
`4 LEAVING`, `5 PROTOCOL_VIOLATION`, `6 PAIRING_FAILED`, `7 RATE_LIMITED`.

Уточнения по реализации (веха 2):

- ALPN: `bridge` — interactive-соединение, `bridge-bulk` — bulk. Принимающая сторона узнаёт класс соединения
  из согласованного ALPN.
- Каждый QUIC-поток начинается с одного байта — тега канала (`ChannelClass::stream_tag`). Control — первый
  bi-поток, его открывает инициатор. Остальные каналы — uni-потоки, их лениво открывает отправитель.
- В TLS 1.3 клиент может завершить свою часть рукопожатия раньше, чем сервер проверит клиентский сертификат.
  Поэтому отказ неспаренному устройству иногда приходит не ошибкой `connect`, а закрытием соединения с
  TLS-алертом `access_denied`. Транспорт превращает его в `NOT_PAIRED`.
- Ответчик становится `Active` на один RTT раньше инициатора, а QUIC не упорядочивает разные потоки между
  собой. Поэтому трафик фич ответчика может обогнать `ServerHello`. Инициатор буферизует такие кадры
  (до 256 штук / 256 КиБ, сверх лимита — `PROTOCOL_VIOLATION`) и обрабатывает их сразу после активации.
- Встречные соединения: если устройства дозвонились друг другу одновременно, остаётся соединение, которое
  инициировало устройство с меньшим `device_id`. Дозвон с повтором (backoff 250 мс → 5 с) не начинается,
  пока с пиром есть живое соединение. Он прекращается навсегда при `NOT_PAIRED`, `REVOKED` и
  `INCOMPATIBLE_VERSION`.

## 4. Ядро

### 4.1. Пиры и сессии

```
           connect/accept                 Hello ok               Paused/Resumed (сигнал пира)
Disconnected ───────────► Handshaking ─────────────► Active ◄──────────────────────► PeerPaused
     ▲                         │ Reject/таймаут        │ потеря связи                      │
     │                         ▼                       ▼                                   │
     └──────── backoff ◄──── Failed              Lost (переподключение с backoff) ◄────────┘
                                                       │ Leaving от пира
                                                       ▼
                                                     PeerLeft (не переподключаемся, пока пир не объявится снова)
```

`PeerSession` — sans-IO автомат: события `Connected`, `FrameReceived`, `Tick(now)`, `TransportClosed(code)`;
действия `Send(channel, frame)`, `Close(code)`, `NotifyFeatures(PeerUp/PeerDown{reason})`. Причина
`PeerDown` (`Lost`, `Left`, `Paused`, `Revoked`, `Incompatible`) важна фичам: при `Lost` передачи ждут
докачки, при `Left` — встают на паузу, при `Revoked` — удаляются.

Инициатором соединения между A и B всегда становится устройство с меньшим `device_id`; встречные соединения
одновременно не плодятся (второе закрывается с `NORMAL`).

### 4.2. Состояния устройства

| Состояние | Что значит | Видимые эффекты на других устройствах |
|---|---|---|
| `Connected` | Работаем. | — |
| `Paused` | Временная пауза: соединения живы, но курсор не уходит на это устройство и не приходит с него, буфер не синхронизируется. Файлы и MIDI продолжают работать (это явные действия пользователя). | Край экрана к устройству «закрыт», устройство серое в раскладке. |
| `Left` | Вышло из группы: отправляет `Leaving` всем, корректно закрывает MIDI-порты (note-off), ставит передачи на паузу, закрывает соединения с кодом `LEAVING`, mDNS-анонс сменяется на `state=left` и затем снимается. | Раскладка схлопывается, курсор не уходит в пустоту, передачи «на паузе», виртуальные MIDI-порты закрыты. |

`DeviceStateMachine` в `core` принимает команды (`Pause`, `Resume`, `Leave`, `Rejoin`) и события сети
(`NetworkChanged{fingerprint}`), учитывает профили сетей:

- профиль = имя + набор отпечатков сети + `auto_join` + какие устройства ожидаются;
- смена сети на неизвестную → `Left` (причина `NetworkChanged`), на известную с `auto_join` → `Rejoin`;
- отпечаток сети не опирается только на SSID (на Windows 11 24H2+ и macOS 14+ SSID требует разрешения
  геолокации): основной признак — MAC шлюза по умолчанию + подсеть, SSID добавляется, если доступен.
  Подробности — [ADR-0016](adr/0016-network-identity.md).

### 4.3. Маршрутизация ввода и «где курсор»

Каждое устройство с физическими мышью/клавиатурой — **источник** со своим маршрутом. Обычно источник один,
но два одновременно не ломают модель (как две мыши у одного компьютера).

`InputRouter` (на источнике), состояние: `Local` | `Remote { peer, screen, pos: (f64, f64) }` | `Locked`.

```
Local ──(курсор у внешнего края, движение наружу, за краем экран другого устройства, кнопки не зажаты*)──► Remote
Remote ──(виртуальный курсор пересёк край в сторону своего экрана)──────────────────────────────────────► Local
Remote(peer=X) ──(пересёк край к экрану устройства Y)───────────────────────────────────────────────────► Remote(peer=Y)
* зажатая кнопка разрешена, только если идёт перетаскивание файлов (DragSource сообщил о drag).
любое ──(хоткей «вернуть управление», потеря связи с пиром, пир Paused/Left, сторожевой таймер)──────────► Local
```

В режиме `Remote` захват переводится в режим «grab»: события не доходят до локальной ОС, система
отдаёт относительные смещения, курсор паркуется. Позиция виртуального курсора ведётся источником;
движения уходят datagram'ами с **абсолютной** позицией в пикселях экрана получателя и номером `seq`.
Потерянная datagram не вызывает дрейфа, устаревшие (`seq` меньше последнего) отбрасываются.

**Сторожевой таймер:** если сетевой цикл не подтверждает получение событий из потока захвата дольше
1 с, захват сам возвращается в `Local`. Хоткей аварийного возврата обрабатывается прямо в потоке хука, без ядра.
Компьютер нельзя «потерять» из-за зависшего демона.

### 4.4. Инвариант «ничего не залипло»

`KeyTracker` хранит для каждой нажатой физической клавиши и кнопки **адрес доставки** (локально или пир X).

- Отпускание отправляется туда же, куда ушло нажатие, даже если курсор уже на другом устройстве.
- При смене цели старая цель получает `ReleaseAll`. Клавиши, зажатые до перехода, на новой цели не нажимаются;
  их отпускания туда не отправляются.
- Приёмник ведёт свой `InjectedSet` для каждого источника (после замены модификаторов) и сам отпускает
  всё при: `ReleaseAll`, закрытии потока `InputEvents`, `PeerDown` с любой причиной, переходе в `Paused`/`Left`,
  истечении idle timeout QUIC (keep-alive 500 мс, таймаут 3 с).
- Автоповтор клавиш передаётся как `Key { down, repeat: true }`: инъектированное нажатие на Windows само не повторяется.

Property-тест: произвольная последовательность нажатий, отпусканий, переходов, пауз, разрывов и переподключений
→ после физического отпускания всех клавиш или после разрыва у каждого адресата `InjectedSet` пуст.

### 4.5. Геометрия раскладки

- Каждый экран: `{ device, screen_id, px: (w, h), origin_px в виртуальном столе устройства, scale ОС,
  физический размер в мм (EDID, иначе из DPI) }`.
- Общая раскладка — прямоугольники экранов в **физических миллиметрах** (f64). Внутри одного устройства
  переходы между мониторами делает ОС в своих пикселях; между устройствами — по миллиметрам.
- Перевод смещения: `Δmm = Δpx_src / ppmm_src`, `Δpx_dst = Δmm · ppmm_dst` — одинаковая физическая скорость.
- Точка выхода на краю экрана A → мм → точка входа на экране B. Курсор не прыгает по высоте на мониторах
  с разным DPI; обратный переход возвращает в ту же точку (property-тест, допуск < 1 px, дробная часть
  позиции хранится в состоянии и не теряется на округлении).
- Отсутствующие устройства (`Paused`/`Left`/`Lost`): край к ним становится стеной, а если за отсутствующим
  устройством в том же направлении есть присутствующее — переход «пробрасывается» сквозь него
  (раскладка схлопывается без изменения сохранённых координат).
- Раскладка — общая для группы конфигурация с версией (Lamport-часы + `device_id` для разрешения конфликтов).
  Редактировать можно с любого устройства, изменения рассылаются по `Control`.
- Каждое устройство вписывает в раскладку только свои экраны (`set_local_screens`): позиции, заданные
  пользователем, сохраняются, а новое устройство ставится справа от остальных. Кто окажется справа при
  первом знакомстве, зависит от того, чья раскладка победит по версии. Это нормально: окончательное
  расположение задаёт редактор (веха 9).

### 4.6. Синхронизация часов

NTP-подобный обмен по `Control` раз в секунду (в первые 5 с — чаще): `t0, t1, t2, t3` → смещение и RTT.
Берётся медиана смещений из выборок с минимальным RTT в скользящем окне, дрейф — линейной регрессией.
Все метки — монотонные микросекунды от старта процесса (`Instant`), стенные часы не участвуют.

### 4.7. Jitter-буфер MIDI

Событие с меткой отправителя `ts` проигрывается в локальное время `ts − offset + delay`, где
`delay = min_transit + buffer`, `buffer` по умолчанию 3 мс (настраивается; есть адаптивный режим —
p99 вариации задержки за окно, в пределах 0–20 мс). Опоздавшие события проигрываются сразу и считаются;
порядок сохраняется (время проигрывания не убывает). UI показывает задержку (сеть + буфер), джиттер,
процент опозданий.

## 5. Модель расширения

```rust
pub trait Feature: Send + 'static {
    fn descriptor(&self) -> FeatureDescriptor; // id, имя, диапазон версий, классы каналов, право доступа
    fn on_peer_up(&mut self, cx: &mut FeatureCx<'_>, peer: PeerId, version: u16);
    fn on_peer_down(&mut self, cx: &mut FeatureCx<'_>, peer: PeerId, reason: PeerDownReason);
    fn on_message(&mut self, cx: &mut FeatureCx<'_>, peer: PeerId, kind: u16, payload: &[u8]) -> Result<(), FeatureError>;
    fn on_device_state(&mut self, cx: &mut FeatureCx<'_>, state: DeviceState);
    fn on_tick(&mut self, cx: &mut FeatureCx<'_>, now: Micros);
}
```

Дополнительные необязательные методы (реализованы в вехах 2–4a): `on_datagram`, `on_tick`,
`on_layout` (сменилась общая раскладка), `on_peer_update` (пир изменил права для нас или своё состояние),
`on_local` (событие извне сетевого цикла — например, пробуждение из потока хука ввода через
`NodeBuilder::local_sender`).

`FeatureCx` даёт: отправку сообщения пиру в канал фичи, таймеры, метрики, проверку прав пира.
Фичам, которым нужен тяжёлый I/O (файлы), `FeatureCx` выдаёт хэндлы потоков; сам I/O идёт в задачах tokio
фичи, а в автомат возвращаются только события. Регистрация:

```rust
let node = NodeBuilder::new(config)
    .feature(InputFeature::new(platform.input()))
    .feature(ClipboardFeature::new(platform.clipboard()))
    .feature(FilesFeature::new(platform.drag_source(), platform.drop_target()))
    .feature(MidiFeature::new(platform.midi()))
    .build()?;
```

Права — открытый набор `PermissionId(u16)`: известные `INPUT`, `FILES`, `CLIPBOARD`, `MIDI`; новые фичи
объявляют свои без правки ядра. Право означает «что **я** разрешаю этому пиру делать **со мной**»: принимать
от него ввод, файлы, буфер, MIDI. Для своих устройств при сопряжении по умолчанию всё включено.

Диапазоны `FeatureId`: `0` — ядро, `1–255` — встроенные (1 input, 2 clipboard, 3 files, 4 midi),
`256–32767` — будущие встроенные (аудио, уведомления, Wake-on-LAN…), `32768+` — плагины.

Точки расширения под «Будущее» — [docs/ROADMAP.md](ROADMAP.md), раздел «Точки расширения».

## 6. Транспорт

```rust
pub trait Transport: Send + Sync + 'static {
    fn caps(&self) -> TransportCaps; // datagrams, max_datagram, класс полосы, задержка, «близость»
    fn connect(&self, addr: PeerAddr, expect: ExpectedPeer) -> BoxFuture<'_, Result<Box<dyn Connection>>>;
    fn accept(&self) -> BoxFuture<'_, Result<Box<dyn Connection>>>;
}
pub trait Connection: Send + Sync {
    fn peer_identity(&self) -> &DeviceIdentity;
    fn open_uni(&self, class: ChannelClass) -> BoxFuture<'_, Result<Box<dyn SendStream>>>;
    fn accept_uni(&self) -> BoxFuture<'_, Result<Box<dyn RecvStream>>>;
    fn open_bi(&self, class: ChannelClass) -> BoxFuture<'_, Result<(Box<dyn SendStream>, Box<dyn RecvStream>)>>;
    fn send_datagram(&self, data: Bytes) -> Result<()>;
    fn recv_datagram(&self) -> BoxFuture<'_, Result<Bytes>>;
    fn stats(&self) -> PathStats; // rtt, потери, полоса, класс пути
    fn close(&self, code: CloseCode, reason: &str);
}
```

Реализации: `quic` (продакшн), `mem` (тесты логики без сети). Симулятор сети — это не отдельный транспорт,
а виртуальный UDP-сокет для quinn в `testkit`, поэтому сбои проверяются на настоящем QUIC.
`ble`, `wifi_direct`, `cable`, `relay` — модули с трейтом-заглушкой и `TODO(roadmap#…)`, без кода «будто работает».

Будущее бесшовное переключение каналов: сессия (`PeerSession`) уже отделена от соединения и
идентифицируется `session_id`; `resume` в `ClientHello` позволит перенести её на другое соединение
без сброса состояния фич. Реализация — в ROADMAP.

## 8. Функции

### 8.1. Ввод

Сообщения `InputEvents`: `Enter { screen, pos, modifiers_state, layout }`, `Leave`, `Key { hid_usage, down, repeat }`,
`Button { button, down }`, `Wheel { dx, dy, hi_res }`, `ReleaseAll`, `SetLayout { lang, layout_id }`.
`InputMotion` (datagram): `{ seq, screen, x, y }`.

- Клавиши кодируются **кодами USB HID (Usage Page 0x07)** — физическая позиция, не символ. Символ даёт
  активная раскладка приёмника, поэтому раскладка синхронизируется при входе курсора (`SetLayout`).
- Замена модификаторов делается на приёмнике (он знает свою ОС): Ctrl↔Cmd при управлении macOS
  с не-macOS, настраивается на пару «источник → я».
- Хоткеи по умолчанию (настраиваются): блокировка курсора на экране — `Ctrl+Alt+L`; перейти на устройство N —
  `Ctrl+Alt+F1…F9`; аварийный возврат — `Ctrl+Alt+Shift+Esc` (обрабатывается в потоке хука).
- Кнопка мыши зажата и это не перетаскивание файлов → переход через край запрещён (курсор упирается в край).
- «Встряхни мышь»: детектор смены направления в `core` → оверлей-локатор на устройстве с курсором
  и подсказка «курсор на Laptop» на остальных.
- Android-тачпад: телефон — источник без собственного экрана в раскладке; жесты переводятся в относительные
  смещения на выбранном компьютере, клавиатура телефона — в `Key`/текстовый ввод.

### 8.2. Буфер обмена

`Offer { seq, origin, formats: [(Format, size)] }` рассылается пирам с правом `CLIPBOARD`, если буфер включён
для этого пира. Получатель объявляет форматы в своём буфере с отложенной выдачей. Текст/HTML/RTF до 256 КиБ
отправляются сразу вместе с предложением, остальное и изображения (PNG) — по запросу при вставке, файлы —
лениво через движок файлов. Лимит размера на пира. Собственные изменения буфера не возвращаются эхом
(сравнение `origin/seq`). Содержимое, помеченное менеджерами паролей как скрытое
(`ExcludeClipboardContentFromMonitorProcessing`, `org.nspasteboard.ConcealedType`,
`x-kde-passwordManagerHint`), не синхронизируется.

### 8.3. Файлы

- `Offer { transfer_id: u128, items: [{ path: [Component], size, mtime, kind }], total }`. Компоненты пути
  валидируются **при декодировании и ещё раз перед записью** (см. 10.4).
- Данные: uni-stream на bulk-соединении, заголовок `{ transfer_id, item, offset }`, затем сырые байты;
  в конце — BLAKE3 всего файла. Чтение и запись блоками по 256 КиБ с backpressure — файлы > 10 ГБ не грузятся в память.
- Приёмник пишет в `.<имя>.bridgepart` рядом с назначением, сохраняет `sidecar` с `transfer_id`, размером и mtime
  источника; по завершении — проверка хеша, установка mtime, атомарное переименование.
- Докачка: после переподключения приёмник шлёт `Resume { transfer_id, item, offset }`; обе стороны дохешируют
  префикс локально. Файл-источник изменился (размер/mtime) → передача этого файла начинается заново.
- Конфликты имён: по умолчанию `имя (1).ext`, варианты — заменить/пропустить. Символические ссылки в источнике
  не разворачиваются (пропускаются с предупреждением).
- Отмена: `Cancel { transfer_id }` + сброс потока с кодом `CANCELLED`, частичные файлы удаляются.
- Отправка без перетаскивания: UI, `bridge send`, контекстное меню проводника (Windows, опционально).

**Перетаскивание** ([ADR-0008](adr/0008-drag-and-drop.md)):

```
 A (источник drag)                                      B (приёмник)
 пользователь тянет файлы к краю
 DragSource: drag вошёл в невидимое окно у края → список путей
 InputRouter: переход разрешён (идёт drag)
 Control: DragStart{transfer_id, items} ─────────────►  DropTarget: инъекция «кнопка нажата» + DoDragDrop /
 Bulk: файлы сразу начинают передаваться ───────────►  NSDraggingSession / XDND-источник, данные пишутся в staging
 движения мыши (datagrams) ─────────────────────────►  ОС ведёт drag под курсором, цели подсвечиваются
 отпускание кнопки (InputEvents) ───────────────────►  drop: цель забирает данные (FILECONTENTS-поток читает staging,
                                                        ожидая недошедшие байты; CF_HDROP/file URL — готовые файлы)
                         ◄────────────────────────────  DropResult{Copied | Cancelled}
 A завершает свой drag-цикл (drop в невидимое окно с DROPEFFECT_NONE) — у источника ничего не перемещается
 Esc в любой момент → Cancel
```

### 8.4. MIDI

- На устройстве с инструментом пользователь выбирает входы/выходы для проброса и пиров.
- Приёмник создаёт виртуальный порт «<имя порта> via <имя устройства>» (источник для DAW), и обратный —
  приёмник, который DAW видит как выход, его данные уходят на физический выход инструмента.
- События — сырые сообщения MIDI 1.0 с валидацией статусов, SysEx до 64 КиБ, ограничение частоты.
  Формат UMP/MIDI 2.0 — расширение (новая версия фичи).
- Приёмник отслеживает удерживаемые ноты и педаль: при разрыве отправляет note-off и CC64=0 в виртуальный порт.
  Порт при коротком разрыве (< 10 с) остаётся открытым и молчит (DAW не теряет устройство), при `Left` или
  долгом разрыве закрывается; при возвращении пира — открывается снова с тем же именем.

## 9. Обнаружение и сопряжение

Подробности — [ADR-0004](adr/0004-identity-and-pairing.md).

- Идентичность устройства — самоподписанный сертификат (ECDSA P-256). `device_id` = SHA-256 от SPKI,
  показывается пользователю как короткий отпечаток.
- mDNS: служба `_bridge._udp.local.`, TXT: `id` (отпечаток), `name`, `proto`, `state`. Имя устройства в анонсе
  можно скрыть (приватность). Ручное добавление по `IP:порт`.
- Сопряжение по 6-значному коду: ответчик открывает окно сопряжения (2 минуты, одна попытка на код),
  показывает код; инициатор вводит его. Внутри TLS-соединения выполняется **SPAKE2** по коду, затем обе стороны
  обмениваются MAC от ключа PAKE поверх транскрипта, включающего **отпечатки обоих сертификатов**.
  Атакующий посередине не может подобрать код офлайн и не может подменить сертификат незаметно.
- QR-код содержит отпечаток ответчика, адреса и одноразовый 128-битный секрет (вместо 6 цифр) — сканирующий
  сразу закрепляет сертификат.
- После сопряжения: запись в хранилище доверия `{ device_id, name, отпечаток, права, профили, last_seen }`.
  Отзыв доверия удаляет запись, рвёт соединения с `REVOKED` и уведомляет пира (лучшее усилие).

## 10. Модель угроз

### 10.1. Активы

Нажатия клавиш (включая пароли), содержимое буфера, файлы, закрытые ключи устройств, **право инъекции ввода**
(фактически полное управление компьютером), MIDI-поток (низкая ценность, но может ронять DAW).

### 10.2. Нарушители

| Нарушитель | Возможности |
|---|---|
| Пассивный слушатель в сети | Видит весь трафик Wi-Fi/LAN. |
| Активный атакующий в сети | ARP/mDNS-спуфинг, MITM, подключение к нашим портам, флуд. |
| Неспаренное вредоносное устройство | Знает протокол, подключается, шлёт произвольные байты. |
| Скомпрометированное спаренное устройство | Имеет валидный сертификат и права. |
| Локальный процесс другого пользователя | Пытается подключиться к IPC демона. |
| Подсматривающий при сопряжении | Видит код на экране. |

### 10.3. Угрозы и меры

| Угроза | Меры |
|---|---|
| **Перехват нажатий** в сети | Только QUIC/TLS 1.3; режима без шифрования нет. В mDNS — только отпечаток и имя (имя можно скрыть). |
| Перехват нажатий через логи и дампы | События ввода и содержимое буфера никогда не пишутся в журнал ни на каком уровне (типы с `Debug` без содержимого); отладочный дамп протокола их маскирует. |
| **Подмена устройства** (mDNS-спуфинг, чужой IP) | Соединение проходит только с закреплённым отпечатком; имя из mDNS — подсказка, не идентичность. Смена сертификата пира = «неизвестное устройство», требуется повторное сопряжение. |
| MITM при сопряжении | SPAKE2 + привязка обоих отпечатков к транскрипту; QR — прямое закрепление отпечатка. |
| Подбор кода | Одна попытка на код, окно 2 мин, открывается только явно на ответчике, блокировка после 3 неудач подряд на 5 мин. |
| **Вредоносный пир в той же сети** (неспаренный) | До проверки отпечатка не обрабатывается ни одного прикладного байта; вне окна сопряжения TLS-рукопожатие отклоняется верификатором. Лимит одновременных рукопожатий, rate limit по IP, QUIC Retry для проверки адреса (нет усиления). |
| Скомпрометированный спаренный пир | Права по умолчанию для своих устройств можно сузить; отзыв мгновенно рвёт соединение. Входящие данные валидируются как от недоверенного источника (ниже). Нельзя навязать запуск файла: файлы только сохраняются. |
| **Path traversal** в именах файлов | Путь передаётся как список компонентов. Отклоняются: пустые, `.`, `..`, содержащие `/`, `\`, `NUL`, управляющие символы, `:` (ADS), зарезервированные имена Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1–9`, `LPT1–9`, в т.ч. с расширением), завершающие точка/пробел, абсолютные пути и префиксы дисков/UNC, компонент > 255 байт, глубина > 64. Нормализация NFC. Итоговый путь проверяется на нахождение внутри папки назначения; существующие компоненты-симлинки не проходятся. Fuzz-цель и тесты на попытки обхода. |
| Исчерпание диска | Проверка свободного места до приёма, лимит размера на пира, для чужих (не своих) устройств — подтверждение приёма. |
| Бомбы в декодере | Лимит кадра до выделения памяти, лимиты длин коллекций, нерекурсивные типы, `checked_*` арифметика в геометрии и смещениях файлов, лимиты на размеры изображений (пиксели) до декодирования. Фаззинг всех декодеров. |
| Флуд ввода/буфера/MIDI | Ограничение частоты сообщений на класс канала; превышение → `PROTOCOL_VIOLATION`. |
| Злоупотребление локальным IPC | Сокет/канал доступен только текущему пользователю, проверка UID/SID клиента. Вредоносный код от имени того же пользователя вне модели (он и так может ставить хуки). |
| Кража закрытого ключа | Файл ключа с правами только владельца; отзыв на остальных устройствах. Хранение в Keychain/DPAPI/Secret Service — в ROADMAP. |
| Утечка паролей через буфер | Скрытые форматы менеджеров паролей не синхронизируются. |
| Цепочка поставок | `cargo-deny` (лицензии, RustSec, источники), `Cargo.lock` в репозитории, actions закреплены по SHA. |
