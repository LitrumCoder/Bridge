# ADR-0008. Перетаскивание файлов между устройствами

Статус: Принято (веха 6b: Windows, X11; виртуальные файлы и macOS — позже)

## Контекст

Пользователь тянет файлы в Проводнике/Finder, уводит курсор за край и отпускает в любую папку или окно
программы (например, DAW) на другом устройстве. Передача должна стартовать в момент начала перетаскивания,
работать с файлами > 10 ГБ и не требовать ожидания там, где это возможно.

## Решение

Роли в терминах Bridge:
- `DragSource` — «drag уходит с этого устройства»: у внешних краёв, за которыми есть другое устройство,
  держатся невидимые окна-цели. Когда курсор с зажатой кнопкой подходит к краю, система доставляет нашему
  окну `DragEnter` с данными — читаем список путей. После завершения drag на другом устройстве
  локальный drag-цикл завершается сбросом в это же окно с эффектом «ничего» (у источника ничего не перемещается).
- `DropTarget` — «drag приходит на это устройство»: инъектируем нажатие кнопки и запускаем системную drag-сессию,
  курсор ведётся инъекцией движений.

Данные: `DragStart` и сразу запуск передачи в **staging**-каталог приёмника на bulk-соединении.

| ОС | Что получает цель | Поведение для больших файлов |
|---|---|---|
| Windows | `IDataObject` (поток STA, `OleInitialize`, `DoDragDrop`) с `CFSTR_FILEDESCRIPTORW` + `CFSTR_FILECONTENTS` (IStream читает staging и ждёт недошедших байт) и `CF_HDROP` с путями staging, рендерится лениво | `CF_HDROP` объявляется, только если суммарный размер ≤ порога (по умолчанию 2 ГБ) — иначе цель ждала бы весь файл. Выше порога — только виртуальные файлы. |
| macOS | `NSFilePromiseProvider` (подкласс добавляет `public.file-url` на файл в staging, когда тот готов); `writePromiseTo:completionHandler:` асинхронный — дописываем по сети и вызываем completion | Finder получает файл потоком. |
| X11 | XDND-источник, `text/uri-list` на staging | Дождаться завершения после drop с оверлеем прогресса; XDS (direct save) — ROADMAP. |
| Wayland | Бесшовный drag невозможен (нет инъекции drag между клиентами без фокуса) | Сохранение в выбранную папку + уведомление. |

Если файл требуется цели до окончания передачи (CF_HDROP, file URL, uri-list), показывается оверлей прогресса
у курсора с отменой по Esc. Отмена в любой момент: `Cancel`, staging очищается.

## Реализация (веха 6b)

- **Роутер ввода.** Пока фича файлов держит флаг «идёт перетаскивание файлов»
  (`InputControl::set_drag_active`), курсор переходит край с зажатой кнопкой.
  - При входе на устройство B роутер шлёт туда «левая кнопка нажата», чтобы ОС B вела свою drag-сессию.
  - Отпускание кнопки идёт **в обе стороны**: локально — чтобы закончился drag-цикл A (над окном Bridge, где
    сброс ничего не делает), и на B — там происходит сброс.
  - До сброса курсор не может уйти с B.
- **Фича файлов.** `DragSink::drag_entered(paths)` от платформы A → обход путей → флаг в роутере. Событие
  роутера `Entered(B)` → `DragOffer` с теми же `Items` → `DragSource::hold()`.
  - B кладёт файлы в staging (`<data>/staging/<id>/`) и сразу вызывает `DropTarget::begin` с корневыми
    элементами.
  - Цель получает пути при сбросе. ОС-обработчик ждёт `DropProgress::wait_complete`, то есть пока передача не
    закончится.
  - Итог сброса (`DragResult`) возвращается на A → `finish()`. Отмена сброса отменяет передачу и чистит staging.
  - Staging хранится неделю: DAW может ссылаться на файл на месте.
- **Windows** (`windows` 0.62, `#[implement]`).
  - Источник: 4 полосы по 2 px вдоль краёв виртуального рабочего стола. Это layered-окна с альфой 1: невидимы,
    но участвуют в hit-test. Они — OLE drop target и показываются, только пока зажата левая кнопка (опрос
    50 мс), чтобы клики у самого края доходили до приложений. При `hold` поверх всего открывается окно на весь
    рабочий стол.
  - Приёмник: поток STA, ожидание нажатия кнопки (до 2 с — нажатие и `DragOffer` идут разными потоками),
    `DoDragDrop` с `IDataObject`, который отдаёт только `CF_HDROP`.
  - **Виртуальные файлы** (`FILEDESCRIPTORW`/`FILECONTENTS`) не сделаны (`TODO(M6b+)`). Сброс любых размеров
    ждёт полной передачи. Оверлей прогресса — веха 9.
- **X11** (`linux_x11/dnd.rs`).
  - Источник — XDND-цель: input-only полосы с `XdndAware`, которые отображаются при зажатой кнопке 1. Они
    читают `text/uri-list`, отвечают на `XdndStatus` и отказывают в `XdndDrop`.
  - Приёмник — XDND-источник под инъектируемым курсором: ищет самое глубокое окно с `XdndAware`, отправляет
    Enter/Position/Leave/Drop и отдаёт `text/uri-list` после завершения передачи.
  - Нативный тест под Xvfb/WSLg проверяет, что обе роли говорят друг с другом.
- **Wayland** — `native_drag()` отдаёт `Unsupported`. `DragOffer` принимается как обычная передача в папку
  загрузок. На стороне источника перетаскивание с Wayland-устройства недоступно.
- **macOS** — в конце этапа (ROADMAP).
- Spike «`DoDragDrop` под `SendInput`» на этой машине не запускался: drag по живому рабочему столу владельца
  мог бы скопировать файлы. Он вынесен в MANUAL_TESTS (D1–D3).

## Альтернативы

- **Только виртуальные файлы (FILECONTENTS/promise).** Многие программы (часть DAW, редакторы) принимают только
  реальные пути — не выполнили бы требование «в окно любой программы».
- **Только реальные файлы.** Ожидание всей передачи до drop — для 10 ГБ неприемлемо.

## Последствия и риски

- То, что `DoDragDrop` корректно ведётся инъекцией через `SendInput`, подтверждено практикой Mouse Without Borders,
  но не документировано Microsoft — проверка в первую очередь на вехе «Файлы» (spike), результат в LIMITATIONS.
- Поведение DAW с file promises не документировано (у Logic 11.2 был баг со своими drag'ами, исправлен в 12.0) —
  отдельные пункты в MANUAL_TESTS для Ableton, Logic, Reaper, FL Studio.
- Staging-каталог чистится по LRU и при старте демона.
