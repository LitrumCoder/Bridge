# ADR-0009. Проброс MIDI

Статус: Принято (веха 7; Windows — режим loopMIDI, WMS — после SDK; macOS — позже)

## Контекст

MIDI-инструмент подключён к устройству A; DAW на устройстве B должна видеть его как локальный вход
(и выход — в обратную сторону). Цель: добавленная задержка < 5 мс и стабильный джиттер в хорошей сети,
ни одного потерянного или переставленного события, корректное закрытие портов.

## Решение

### Время
- Синхронизация часов NTP-подобным обменом по `Control` (ARCHITECTURE §4.6), монотонные микросекунды.
- Отправитель ставит метку времени захвата (из колбэка драйвера, если он даёт метку, иначе момент колбэка).
- Приёмник: jitter-буфер, задержка проигрывания = минимальное наблюдаемое время в пути + буфер
  (по умолчанию 3 мс, настраивается 0–20 мс; адаптивный режим — p99 вариации). Опоздавшие события
  проигрываются сразу; время проигрывания не убывает → порядок сохраняется.
- Поток `Midi` надёжный и упорядоченный, на interactive-соединении с приоритетом ниже ввода.

### Безопасное закрытие
- Приёмник отслеживает удерживаемые ноты (канал × нота) и педали; при любом разрыве — note-off и CC64/66/67 = 0.
- Короткий разрыв (< 10 с) — порт остаётся, DAW не теряет устройство. `Left` или долгий разрыв — порт закрывается.
  Возврат пира — порт создаётся снова с тем же именем (DAW, как правило, переподключает по имени).

### Виртуальные порты по ОС

| ОС | Механизм | Библиотека |
|---|---|---|
| macOS 13+ | `MIDISourceCreateWithProtocol` / `MIDIDestinationCreateWithProtocol` (CoreMIDI, macOS 11+) | `objc2-core-midi` или `coremidi` (MIT) — выбор на вехе по фактическому API |
| Linux | ALSA sequencer, порт с `SND_SEQ_PORT_CAP_SUBS_READ/WRITE`; через мост PipeWire виден и JACK-программам | `alsa` (MIT/Apache) → системная `libasound` (LGPL-2.1, динамически, см. ADR-0013) |
| Windows 11 25H2+ | **Windows MIDI Services**: `MidiVirtualDeviceManager` (app-to-app) из WinRT `Windows.Devices.Midi2`. Привязки генерируются `windows-bindgen` из `.winmd` NuGet-пакета SDK (MIT). | `windows`/`windows-bindgen` |
| Windows 10 и Windows 11 без WMS | Пользователь ставит бесплатный **loopMIDI** и создаёт порты `Bridge In`/`Bridge Out` (по одному на направление — порт loopMIDI петлевой); Bridge находит их по имени и работает с ними как с обычными портами. Мастер в UI ведёт по шагам. Мы loopMIDI **не распространяем**. | `midir` (WinMM) |

Физические порты на всех ОС открываются через `midir 0.11` (MIT).

### Открытые вопросы Windows (spike в начале вехи MIDI)
1. Видят ли DAW на WinMM/WinRT MIDI 1.0 (Ableton, FL Studio, Reaper) виртуальные устройства WMS. Документация
   говорит, что служба транслирует между API, но явного подтверждения нет.
2. Нужно ли конечному пользователю ставить «SDK Runtime and Tools» (`winget install Microsoft.WindowsMIDIServicesSDK`)
   или хватает встроенной службы. Если нужно — установщик Bridge проверяет и предлагает установку.
3. SDK официально ещё в статусе preview (API зафиксирован с 0.99.92). Бэкенд изолирован за `MidiPorts`,
   замена не затрагивает ядро.

## Реализация (веха 7)

- **Протокол** (`bridge_protocol::midi`):
  - `Ports { device, ports: [{id, name, direction}] }` — что устройство с инструментом отдаёт;
  - `Events { port, to_instrument, events: [{ts, data}] }`. Идентификаторы портов принадлежат владельцу
    инструмента, `to_instrument` разводит два направления;
  - каждое сообщение проверяется на целостность (статус, длина, SysEx ≤ 64 КиБ с `F7`), метки не убывают.
- **Ядро** (`bridge_core::midi`):
  - `MidiParser` — running status, real-time внутри SysEx, оборванный SysEx отбрасывается;
  - `NoteTracker` — ноты и педали CC64/66/67, `all notes off`;
  - `JitterBuffer` — `ts − offset + min_transit + buffer`. Время проигрывания не убывает, опоздавшие события
    играют сразу и считаются, адаптивный буфер — p99 разброса, до 20 мс;
  - proptest: монотонность, обратимость парсера, отпускание всего.
- В `PeerView` появился `clock_offset` (оценка `ClockSync`).
- **Фича.** Метка захвата — `Instant` из колбэка платформы, она переводится во время узла.
  - У приёмника есть **свой поток проигрывания**: сон до события минус 1 мс, затем короткий спин (тик узла
    слишком груб). На Windows поток включает таймер 1 мс (`bridge_platform::fine_timers`).
  - Без оценки часов события играют по приходу.
  - Отдаются все входы и выходы устройства (`MidiConfig::share`). Выбор портов и пиров — в UI (веха 9).
  - Разрыв: очередь доигрывается, затем note-off и педали в 0, порт молчит 10 с. При `Left` и отзыве порт
    закрывается сразу.
- **Windows.** WinMM через `midir 0.11`. Виртуальные порты — режим loopMIDI: `Bridge In` (мы пишем, DAW читает)
  и `Bridge Out` (DAW пишет, мы читаем). Соединение на порт одно и кэшируется. Все потоки с разных устройств
  сливаются в эти два порта.
- **Spike WMS** (2026-10-27, Windows 11 25H2 на машине разработчика):
  - служба `MidiSrv` работает, транспорты `Midi2.*.dll` в System32 есть;
  - SDK Runtime («Windows MIDI Services» в Program Files) не установлен, метаданных `Windows.Devices.Midi2`
    в `WinMetadata` нет;
  - вывод: виртуальные устройства app-to-app требуют, чтобы пользователь поставил SDK, а нам нужны
    привязки из `.winmd` NuGet-пакета, получить которые без сети нельзя. На этапе 1 — loopMIDI (`TODO(M7+)`).
- **Linux.** ALSA sequencer через `dlopen("libasound.so.2")` и минимальный FFI. Сборка не требует
  `libasound2-dev`, лицензия системной библиотеки соблюдена динамической загрузкой. Виртуальный источник —
  порт `READ|SUBS_READ`, назначение — `WRITE|SUBS_WRITE`, физические порты — через
  `snd_seq_connect_from/to`. Байты ↔ события — `snd_midi_event_*`. Нет библиотеки или `/dev/snd/seq` —
  `Unsupported`.
- **macOS** — в конце этапа.
- **Замеры** (`testkit/tests/midi.rs`, бенчмарк `midi/note_instrument_to_daw_loopback`): на 127.0.0.1 с буфером
  3 мс задержка p50 — 3,18 мс, p99 — 4,0 мс, медиана criterion — 3,11 мс. Через симулятор (потери 5 %,
  джиттер 3 мс) 600 событий с SysEx по 1 КБ дошли все и по порядку.

## Альтернативы

- **teVirtualMIDI SDK.** Проприетарный, распространение только по лицензии автора — отвергнут политикой лицензий.
- **Свой драйвер виртуального MIDI для Windows.** Подпись драйверов, отдельный продукт; не на этапе 1.
- **RTP-MIDI (AppleMIDI) вместо своего протокола.** Есть в macOS, но не решает виртуальный порт на Windows,
  без нашей синхронизации часов и аутентификации. Возможен как дополнительный транспорт позже.
- **Прямые ioctl `/dev/snd/seq` без libasound.** Избавляет от LGPL-библиотеки, но нет готовых примеров и
  поддерживать бинарный ABI ядра самим рискованно. Запасной путь, если исключение ADR-0013 не будет принято.

## Последствия

- Бенчмарк задержки и джиттера на loopback с mock-портами, тест порядка и полноты на сетевом симуляторе с потерями.
- В UI: текущая задержка (сеть + буфер), джиттер, доля опозданий.
- Windows 10: MIDI работает только с loopMIDI — фиксируется в LIMITATIONS и README.
