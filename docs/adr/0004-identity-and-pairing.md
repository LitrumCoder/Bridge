# ADR-0004. Идентичность устройств и сопряжение

Статус: Предложено

## Контекст

Нужны взаимная аутентификация без центрального сервера и CA, сопряжение по 6-значному коду или QR-коду,
стойкое к атакующему в той же сети, закрепление сертификатов и отзыв доверия.

## Решение

- **Ключ и сертификат устройства:** ECDSA P-256, самоподписанный, генерируется `rcgen 0.14` при первом запуске.
  P-256 выбран вместо Ed25519 из-за самой широкой поддержки в rustls/ring для подписи TLS 1.3 на всех платформах.
- **`device_id` = SHA-256(SPKI)**; пользователю показываются первые 8 символов base32 как отпечаток.
- **Хранилище доверия** (`trust.toml` в каталоге конфигурации): `device_id`, имя, права, профили, `last_seen`.
  Закрытый ключ — отдельный файл с правами только владельца. Перенос в Keychain/DPAPI/Secret Service — ROADMAP.
- **Окно сопряжения** открывается явно на ответчике (UI/CLI `bridge pair --show`), длится 2 минуты.
  Только в окне верификатор пропускает неизвестный сертификат, и только для `intent: Pair`.
- **Протокол сопряжения по коду** (внутри уже установленного TLS-соединения):
  1. ответчик генерирует код из 6 цифр (20 бит) и показывает его;
  2. обе стороны выполняют **SPAKE2** (`spake2 0.4`, RustCrypto) с паролем = код и идентичностями =
     `device_id` инициатора и ответчика;
  3. из общего ключа выводятся ключи подтверждения (HKDF), стороны обмениваются
     `HMAC(k, "bridge-pair-v1" ‖ fp_A ‖ fp_B ‖ transcript_hash)`, где `fp` — отпечатки сертификатов,
     **увиденные в TLS-рукопожатии**;
  4. совпадение → обе стороны записывают пира в хранилище доверия с правами по умолчанию.
  Атакующий посередине видит разные сертификаты у сторон, и MAC не сойдётся. Перебор кода только онлайн,
  одна попытка на код, после 3 неудач подряд — блокировка окна на 5 минут.
- **QR-код:** `bridge://pair?fp=<отпечаток>&addr=<ip:port,…>&s=<128-битный секрет base32>`. Сканирующий
  закрепляет отпечаток сразу, в SPAKE2 используется секрет вместо 6 цифр.
- **Отзыв:** удаление записи → закрытие соединений с `REVOKED` → пиру уходит `Unpaired` (если он онлайн).
  Неотозванный ключ на украденном устройстве отзывается на всех остальных вручную.

## Альтернативы

- **Сравнение кода без PAKE** («введите код, который видите»). Код легко подобрать офлайн по перехваченному
  транскрипту, если он участвует в хеш-проверке. PAKE исключает офлайн-перебор.
- **SAS как в Bluetooth Numeric Comparison** (обе стороны показывают 6 цифр от хеша отпечатков, пользователь
  сравнивает). Стойко, но требует экранов на обеих сторонах одновременно; оставлен как будущая опция.
- **Собственный CA группы устройств.** Удобнее для отзыва, но вводит «главное» устройство, которого у нас нет.

## Реализация (веха 3)

- Сообщения `PairStart { method: Code | QrSecret, spake }` и `PairConfirm { mac }` (kind 12 и 13 ядра).
  SPAKE2 на Ed25519 (`spake2 0.4`, без `getrandom`: случайность передаёт драйвер через трейт `Entropy`,
  ядро не обращается к ОС). Идентичности SPAKE2 — `device_id` из TLS-сертификатов. Подтверждение —
  `HMAC-SHA256(K, "bridge-pair-v1" ‖ сторона ‖ id инициатора ‖ id ответчика)`, сравнение за постоянное время.
- Окно сопряжения на ответчике: 2 минуты, одно успешное или неуспешное сопряжение закрывает его.
  Три неудачи за 5 минут — блокировка на 5 минут. Пока окно открыто, TLS-верификатор пропускает
  неизвестные сертификаты, но ядро не допускает в таком соединении ничего, кроме обмена сопряжения.
- QR: `bridge://pair?fp=<id>&addr=<ip:port>&s=<секрет base32>`. Сканирующий дозванивается с
  `ExpectedPeer::Device(fp)`, то есть отпечаток закреплён ещё до PAKE.
- Хранилище доверия: `trust.toml` в каталоге данных; записывается атомарно (через временный файл).
- Тесты: ретранслятор с разными сертификатами при верном коде — отказ (`pairing::tests`), неверный код,
  закрытое окно, блокировка, QR, снятие сопряжения у обеих сторон, изменение прав на живом соединении.

## Последствия

- В интеграционных тестах: успешное сопряжение, неверный код, MITM-прокси (testkit подменяет сертификат),
  отказ неспаренному, истечение окна.
- Фаззинг сообщений сопряжения.
