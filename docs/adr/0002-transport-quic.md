# ADR-0002. Транспорт: QUIC (quinn) + rustls, два соединения на пару

Статус: Принято (bulk-контроллер — веха 6a)

## Контекст

Нужны в одном канале: ненадёжная доставка для движений мыши, несколько надёжных упорядоченных потоков
без head-of-line blocking между ними (клавиши, MIDI, буфер, файлы), шифрование и взаимная аутентификация,
работа через NAT-подобные домашние сети без настройки. Передача больших файлов не должна увеличивать
задержку ввода и MIDI.

## Решение

- **quinn 0.11** (проверено: `Connection::send_datagram`/`read_datagram`/`max_datagram_size`,
  `SendStream::set_priority(i32)`, по умолчанию 0, данные с бо́льшим приоритетом уходят раньше).
- **rustls 0.23 с провайдером `ring`**, а не с провайдером по умолчанию `aws-lc-rs`. Причины: в лицензионном
  выражении `aws-lc-sys` есть MIT-0 (не входит в разрешённый список), сборка aws-lc на Windows и под Android
  требует cmake/nasm. `ring` — `Apache-2.0 AND ISC`. Риск: последний релиз ring — 2025-03; если провайдер
  перестанет поддерживаться, переход на aws-lc-rs — замена одной строки конфигурации и пересмотр ADR-0013.
- TLS 1.3 (обязателен в QUIC), ALPN `bridge`, сертификаты устройств на обеих сторонах, собственные
  `ServerCertVerifier`/`ClientCertVerifier` с закреплением отпечатка SPKI (ADR-0004). Подпись
  `CertificateVerify` проверяется штатными функциями rustls — владение ключом доказывается.
- **Два соединения на пару устройств через один UDP-сокет:**
  - `interactive` — Control, InputMotion (datagrams), InputEvents, Midi, Clipboard; контроллер перегрузки по умолчанию;
  - `bulk` — только файлы; собственный `quinn::congestion::Controller` с ограничением по задержке
    (LEDBAT-подобный: окно уменьшается, когда RTT превышает базовый на 5 мс). Приоритеты потоков
    не помогают против очереди в роутере — помогает только то, что bulk-трафик сам держит очередь короткой.
- Keep-alive 500 мс, idle timeout 3 с на interactive (быстрое обнаружение разрыва → отпускание клавиш), 30 с на bulk.
- QUIC Retry для неизвестных адресов, лимит одновременных рукопожатий.
- Порт по умолчанию 47800/udp, при занятости — любой свободный, фактический порт объявляется в mDNS.

## Реализация bulk (веха 6a)

- `bridge_transport::Ledbat` реализует `quinn::congestion::Controller`. Для типа `RttEstimator` в сигнатуре
  нужна прямая зависимость `quinn-proto`. Логика:
  - замер — `now − sent` каждого подтверждения;
  - базовая задержка — минимум по 6 корзинам за 60 с;
  - текущая задержка — минимум последних 16 замеров. В RFC 6817 их 4, но отложенные ACK и грубые таймеры ОС
    (Windows по умолчанию — 15,6 мс) дают шум, который не должен читаться как очередь;
  - цель — +5 мс;
  - рост аддитивный (`gain · off_target · MSS` за RTT), slow start — пока очередь < цели/2;
  - при превышении цели окно уменьшается **мультипликативно**, не чаще раза за RTT (как в LEDBAT++). По
    RFC окно снижалось бы линейно, и разогнанное окно освобождало бы очередь минутами;
  - потеря — окно пополам, раз за окно потерь;
  - минимальное окно — 2 пакета.
- Контроллер ставится только в клиентскую конфигурацию bulk-соединения. Каждая сторона дозванивается своим
  bulk-соединением, чтобы отправлять. Принятые bulk-соединения только принимают потоки, поэтому серверной
  конфигурации (общей для всех ALPN) контроллер не нужен. Окна приёма bulk: 8 МиБ на поток, 16 МиБ на
  соединение.
- Узел (`BulkHub` в `bridge-daemon`) дозванивается лениво, на адрес interactive-соединения пира, и
  переподключается при ошибке. Входящие bulk-потоки с тегом `Bulk` уходят в фичу файлов
  (`NodeBuilder::bulk()`).
- Проверка (`testkit/tests/netsim_bulk.rs`, горло 40 Мбит/с, очередь 1 МБ, задержка 5 мс):
  - p99 пинга по interactive во время передачи — 15,7 мс при базовых 13,1 мс, скорость 30 Мбит/с;
  - тот же трафик со стандартным контроллером — p99 203 мс;
  - по умолчанию передаётся 24 МБ, с `BRIDGE_LONG_TESTS=1` — 2 ГБ;
  - на Windows тест включает таймер 1 мс (`timeBeginPeriod`), иначе симулятор шумит на 15,6 мс.

## Альтернативы

- **TCP + TLS + свой мультиплексор, UDP для мыши.** Head-of-line blocking между потоками, два механизма
  шифрования, больше кода.
- **WebRTC (DataChannel).** Хорош для будущего веб-клиента, но тяжёлый стек (ICE/DTLS/SCTP) избыточен в LAN.
  Будет отдельной реализацией `Transport` (ROADMAP).
- **Одно соединение с приоритетами потоков.** Проще, но под нагрузкой файлами задержка ввода растёт из-за
  bufferbloat — это проверено практикой и будет видно в тесте сетевого симулятора.

## Последствия

- Нужно реализовать и протестировать свой контроллер перегрузки для bulk.
- Два соединения = два рукопожатия; bulk поднимается лениво, при первой передаче.
- Сетевой симулятор реализуется как собственная реализация `quinn::AsyncUdpSocket` (ADR-0014), поэтому сбои
  проверяются на настоящем QUIC, а не на модели.
